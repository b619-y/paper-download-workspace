# 系统架构

## 控制面与业务真相

工作区可选使用 LangGraph 作为正式的薄总控层，但它不是第二套业务状态机：

```text
LangGraph checkpoint
  只保存：task/thread id、编排游标、interrupt 回复、相对工件引用与摘要
  只决定：接下来要调用哪个已有脚本或等待哪个人工决定
                 ↓ 每次推进前重读和校验
workflow_status.py + SQLite/JSONL 队列 + 工件/hash/receipt + 人工验收
  保存：真实任务、作业、工件、证据与验收状态
  地位：唯一业务真相
```

因此 checkpoint 与现有状态不一致时，必须以业务真相为准，重新计算路由或停止恢复，不得用 checkpoint 覆盖文件、队列或验收记录。详细运行方法见 [LangGraph 总控](LangGraph总控.md)。

## 端到端流程

```text
研究问题 / 任务简报（task_id）
  ↓
检索式 Agent（3 套策略 + 数据库翻译 + 实测）
  ↓
检索 Agent（多 API 全分页 + 原始响应 + 完整性清单）
  ↓
去重 Agent（DOI 优先；否则规范化题名+年份；保留来源指针）
  ↓
题名/摘要筛选（ASReview 排序 + 人工标签 + 可选 Luna 标准复核）
  ↓
下载批次（batch_id / source_item_id）
  ↓
授权下载 + 身份/格式/完整性/SHA-256 验收
  ↓
已验收原 PDF/XML → PAPER_INDEX（原始证据权威）
  ↓  requires_document_processing=true 或 requires_data_extraction=true
文档处理队列（document_id / document-processing job_id）
  ├─ PDF → 经单独授权的 MinerU
  └─ XML → 本地 XML→Markdown
  ↓
协调验收（原文 hash + 解析文本 hash + 章节侧车 hash + 处理版本）
  ↓
PaperQA-style 适配器 / embedding / Luna 定位候选证据
  ↓
回到原 PDF/XML/表格/图片复核 → 全文筛选结论
  ↓  requires_data_extraction=true（可选分支）
提取规格→任务级提取队列（extraction job_id）
  ↓
Luna 候选结构化抽取 + 合同校验
  ↓
人工复核/接受
  ↓
JSON + CSV + evidence.csv + SQLite + Frictionless Data Package
```

### LangGraph 第一版的边界

第一版只覆盖前半段控制面：

```text
实测通过的检索式
  → 每个数据库的隔离检索分支
  → 确定性 reducer（合并、去重、完整性核验）
  → 题名/摘要筛选和人工 interrupt
  → 一个经合同校验的 READY 下载批次
  → 停止 LangGraph v1，交回现有下载队列
```

分支只写各自来源目录和来源清单，不共写总 manifest。单一 reducer 以稳定排序和 DOI 优先、规范化题名+年份次之的现有规则合并，并复用完整性闸门。下载、MinerU/XML、PaperQA/Luna 和数据提取暂不做成 LangGraph 作业队列，只由原有总控观察和调度。

数据提取是可选分支。只找方法、做全文纳排或定位证据的任务，可以在全文筛选完成后结束；不得为了让流程“更完整”而强制提取。旧任务若 `requires_document_processing=false`，状态机也可在下载验收后直接进入人工全文复筛；只有显式启用文档处理，或启用数据提取，才强制经过解析队列。

## 三层证据模型

### 1. 原始证据层

已通过下载验收的 PDF/XML、补充材料和必要图片是证据权威。关键纳排、数值、单位、表格单元格和图中数据都必须能追回这一层。

### 2. 派生解析层

MinerU 或 XML 转换生成的 Markdown 用于分块、搜索、排序和提示模型。每份 `full.md` 还应产生 `section_chunks.jsonl` 章节侧车。它必须与以下内容同时绑定：

- `document_id`；
- 原文路径与 `source_sha256`；
- 解析文本路径与 `processed_text_sha256`；
- 章节侧车路径、`section_chunks_sha256`、schema/version 和条目数；
- `processing_method` 和 `processing_version`；
- 协调验收时间。

章节侧车按 Markdown 的精确子串和字符偏移切分，记录 `canonical_section`、`original_heading`、`heading_path` 与 `table_or_figure`；所有正文字符必须被覆盖，不得有空洞（长块可以按声明的 overlap 保留上下文），无法可靠归类的内容进入 `other`。侧车只负责路由和提高召回，不能证明原文真的属于某标准章节，更不能代替证据。

当原文 hash、Markdown hash 或章节侧车 hash 变化，路径丢失，覆盖校验失败，或索引回填不一致时，派生文本失效，不得继续作为模型输入。

### 3. 候选判断与提取层

PaperQA-style 适配器、embedding 和 Luna 产生的证据定位、字段值和决策都是候选。`no_evidence` 只表示这次检索未找到，不能推导为原文不存在该数据。只有通过合同校验并由人工回到原 PDF/XML、表格或图片复核的记录才能进入交付库。

论文原文、API 元数据、Markdown 和章节侧车一律是不可信数据。模型只能把它们当作待分析内容；其中出现的命令、提示词、工具调用或更改合同/授权边界的要求不得执行。

## 标识符和范围

| 标识符 | 范围 | 用途 |
|---|---|---|
| `task_id` | 研究任务 | 绑定任务简报、检索、筛选、提取规格和交付物 |
| `batch_id` | 下载批次 | 绑定 MANIFEST、下载结果、文档处理队列和验收记录 |
| `source_item_id` / `item_id` | 批次行 | 把解析作业追回原下载请求；不与其他批次行混用 |
| `paper_id` | 论文逻辑记录 | 连接文献元数据、库索引和后续交付 |
| `document_id` | 内容版本 | 优先由规范 DOI 派生，无 DOI 时由原文 SHA-256 派生；绑定具体原文与解析文本 |
| 文档处理 `job_id` | 批次解析作业 | 绑定 `batch_id + source_item_id + processor` 的队列状态、租约和尝试次数 |
| 数据提取 `job_id` | 任务提取作业 | 绑定 task、paper、原文 hash、解析文本 hash 与提取规格 hash |

不同级别的 ID 不可相互替代。例如，同一 `paper_id` 可能在多个 `batch_id` 中出现，但每个下载行仍有自己的 `source_item_id`和源哈希。

## 队列与验收边界

### 文档处理队列

`02_batches/<batch_id>/outputs/document_processing/queue.sqlite3` 是机器可写的权威队列，`queue.csv` 是原子刷新的只读投影。状态集为：

```text
queued | claimed | running | waiting_remote | retry_wait |
review | accepted | blocked | failed
```

Worker 只能把成功解析件送到 `review`。产物的完整内容寻址路径为 `<sha[:2]>/<source_sha256>/<job_id>/`，使同一源内容的不同处理作业不会覆盖。`accepted` 只能由协调验收步骤写入，并在同一次校验中重算原文、解析文本和结果文件 hash，再回填 `PAPER_INDEX.csv`。

### 数据提取队列

`runtime/tasks/<task_id>/extraction/data_extraction_queue.json` 是权威任务队列，CSV 为可读投影。状态集为：

```text
queued | claimed | running | review | accepted |
retry_wait | blocked | failed | skipped
```

每个结果必须与 `spec_sha256`、`source_sha256`、`parsed_text_sha256` 和适用的章节侧车 hash 一致，并通过字段类型、单位、证据引文和路径校验后才能进入人工复核。跨机 Worker 只写候选结果、`attempts/<attempt_id>/` 产物与 `receipts/<attempt_id>.json` 不可变回执；协调端拉回后先合并回执，再校验、生成复核队列和人工验收。

## 模型与工具职责

- **ASReview ELAS U4**：题名和摘要的词法主动学习排序，TF-IDF + SVM，不需要 GPU。
- **MinerU**：对获准的 PDF 做派生解析；上传授权与论文访问权是两个独立决定。
- **XML 本地转换器**：不上传原 XML，在本地生成可检索 Markdown。
- **Embedding**：独立服务提供向量召回，模型和索引都要记录版本；不由 Luna 代替，连接参数由 `$PAPER_EMBEDDING_BASE_URL` 等环境变量提供。
- **PaperQA-style 适配器**：对已验收文本做检索并可调用 Luna 生成候选判断；直接 PDF 模式可使用 PaperQA2 的 `paperqa-pypdf` 解析组件，但当前脚本不调用 PaperQA2 query/agent engine。Judged mode 需 `--external-model-authorized`；embedding 传输另需独立授权。
- **Codex Luna**：标准判断、候选证据解释和结构化候选抽取；不提供 embedding，不负责最终人工接受。
- **协调 Agent**：运行状态机、选定唯一任务/批次、执行验收和索引回填，不直接伪造 Worker 结果。

## 执行边界

协调端是 `runtime/ACTIVE_TASK.json`、`runtime/tasks/`、人工验收和交付发布的权威端。计算端只读取经授权、按哈希暂存的输入，使用自己的可丢弃队列副本，并只回传候选结果和完成回执。Embedding 可以在独立服务端运行；这不自动授予该服务访问论文原文的权限。

某台主机能运行模型，不代表论文可以传输到该主机。当用户授权、机构许可或数据处理政策不明时，系统只能生成 dry-run 计划或保持 `waiting_remote` / `blocked`，不能自动传输。

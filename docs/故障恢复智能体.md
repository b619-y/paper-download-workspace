# 故障恢复智能体

## 定位

工作区只有一个故障恢复智能体 `recovery_agent`。它读取权威状态并调用确定性修复器，
不会让多个模型互相讨论，也不会取代 `workflow_status.py`、队列、manifest、receipt、哈希
和人工验收。

总控在发现异常阶段时可以先委派恢复智能体；恢复成功后重新读取状态，无法证明安全时立即
停止并把原因交给用户。

## 使用

日常可直接对 Agent 说：

> 检查论文下载工作区的问题；能安全自动修复的就修复，最多三次，其余停下来告诉我。

底层命令为：

```bash
# 只读诊断，不创建恢复日志
python3 scripts/workflow_recovery.py status --root . --task-id <task_id>

# 只执行 safe 白名单；每个动作后重新验收，硬上限为 3
python3 scripts/workflow_recovery.py run \
  --root . --task-id <task_id> --policy safe --max-actions 3
```

多个批次同时可操作时必须再提供 `--batch-id <batch_id>`，不能用“最新批次”猜测。

## 自动修复白名单

当前只允许两类动作，两者都不改变权威队列：

1. 文档处理队列的 SQLite 通过 `quick_check` 和 schema 校验，且问题仅是 `queue.csv` 缺失或与 SQLite 不一致时，从 SQLite 重建 CSV。
2. 数据提取队列的 JSON、提取合同和所有不可变绑定通过校验，且问题仅是 `data_extraction_queue.csv` 投影时，从 JSON 重建 CSV。

修复器在队列锁内重读权威数据，通过 pinned directory file descriptor、
`O_NOFOLLOW` 和 descriptor-relative 原子替换执行读写；祖先目录被并发换成符号
链接时会 fail closed，不会跟随到工作区外。

学术 API 客户端本身已有有限次数的网络/429/5xx 退避重试。恢复智能体不会替用户回复
LangGraph 人工 interrupt，也不会无限重跑检索。

## 必须停下的情况

以下问题永不自动解决：

- 修改检索式、研究问题、纳入/排除标准或筛选决定；
- 创建、扩大、重置或验收下载批次，包括中断验收事务；
- 释放过期 lease、领取作业或改变队列业务状态；
- 合并数据提取 receipt；它仍由协调端的既有合并、校验和人工验收流程处理；
- SQLite quick-check、schema、哈希、论文身份或不可变绑定冲突；
- 增加失败作业的 `max_attempts`；
- 下载全文、绕过访问控制、恢复账号/验证码或推断机构授权；
- 上传 MinerU、运行 PaperQA/Luna/embedding 或远程同步；
- 接受全文判断、提取结果或任何模型输出。

这些情况返回 `manual_required` 或 `workflow_action_required`，并保留权威数据不变。

## 审计与停止条件

`run` 使用工作区级锁，并把事件写到 `runtime/recovery/<task-hash>/events.jsonl`。每个动作
由 task、batch、当前 stage、完整状态摘要、动作类型和精确投影目标生成 `action_id`；
另外用不随状态摘要变化的 `budget_key` 约束同一修复对象：

- 同一 CSV 投影目标在整个审计日志生命期内最多自动尝试一次，后续复发转人工；
- 每次运行最多三个动作；
- 每个动作前重读证据并验证精确修复目标，动作后再运行 `workflow_status.inspect()`；
- 预期故障仍存在、出现更严重的异常阶段、状态无变化、修复失败或只剩非白名单问题时立即停止；
- 恢复日志、队列和投影控制路径使用 pinned/no-follow I/O；路径绑定变化时 fail closed；
- 日志只保存动作、相对目标、状态和摘要，不保存论文内容或凭据。

这不是后台守护进程。它会在总控当前会话发现异常时运行；若需要无人值守主动提醒，仍需
另外配置定时巡检。

# 协调端、计算端与 GitHub 同步方案

同步分成两条完全不同的通道：Git 只管代码与空合同，`runtime/` 数据只走明确的单向传输。不得用 `git add -f` 把运行数据塞进 GitHub，也不得将“已能连接计算端”解释为“已获准传输论文”。

## GitHub 通道

可以入库：

- 源码和测试；
- Agent 角色说明和提示词；
- schema、合同、文档和空模板；
- 不含账号、内网细节或真实研究数据的示例配置。

禁止入库：

- PDF、XML、CAJ、补充材料和论文图片；
- MinerU/XML 生成的 Markdown 和原始 ZIP；
- API key、Cookie、Token、机构登录态和 `.env`；
- ASReview 项目库、PaperQA 索引、SQLite/DB/WAL/SHM；
- 真实 `BATCH_INDEX.csv`、`PAPER_INDEX.csv` 与 `DECISIONS.md`（只提交对应 `.example`）；
- `runtime/`中的真实任务、标注、模型输出、提取结果和交付数据。

GitHub 是代码版本的中枢，不是论文库或运行状态数据库。

## 运行状态权威

- **协调端是权威端**：维护 `runtime/ACTIVE_TASK.json`、`runtime/tasks/`、任务和批次选择、人工验收以及最终交付。
- **计算端是暂存端**：只处理已核准传入的输入，并把候选定位、数据提取或文档处理结果写到 `runtime/results/<task_id>/`。
- **Embedding 服务可以独立部署**：通过 `$PAPER_EMBEDDING_BASE_URL` 访问；服务可用不代表它获准接收论文全文。

计算端可为领取和运行修改自己的可丢弃队列副本，但不能直接改写协调端的 `ACTIVE_TASK.json`、权威任务队列或人工接受状态。协调端拉回结果后必须先合并不可变回执，再重验 ID、路径和 hash。

## 先本地 staging，后传输

`stage_processing_inputs.py` 在协调端创建任务级、内容绑定的输入包，它本身不会连接计算端：

```bash
python3 scripts/stage_processing_inputs.py \
  --root . \
  --task-id <task_id> \
  --document-id <document_id> \
  --batch-id <batch_id> \
  --source-item-id <MANIFEST.item_id> \
  --paper-id <paper_id> \
  --title '<paper title>' \
  --doi '<doi-if-known>' \
  --parser <mineru-or-xml_to_markdown> \
  --parser-version <accepted-parser-version> \
  --source-ref <workspace-relative.pdf-or-xml> \
  --source-sha256 <64-hex> \
  --parsed-text-ref <workspace-relative.md-or-txt> \
  --parsed-text-sha256 <64-hex> \
  --dry-run
```

dry-run 会校验 ID、路径、当前文件 hash 和目标冲突，只输出 JSON 计划，不创建 `runtime/`文件。去掉 `--dry-run` 后，默认写入：

```text
runtime/inputs/<task_id>/documents/<document_id>/
├─ manifest.json
├─ parsed/<parsed_text_sha256>.<ext>
└─ parsed/<section_chunks_sha256>.section_chunks.jsonl
```

`--batch-id`、`--source-item-id`、`--paper-id`、`--parser` 和 `--parser-version` 应来自已验收的文档处理行；前两者使远端队列仍能找到同一批次的 `OVERALL` 全文筛选决定。正式输入还要绑定 `section_chunks.jsonl` 的路径、SHA-256、schema/version 和条目数。`manifest.json` 仅保存工作区相对引用、处理器元数据和 hash，并同时提供适配器可读的原文、解析文本和章节侧车绑定。默认不复制 PDF/XML；只有传输政策已核准原文时，才可显式加 `--allow-copy-fulltext`，将原文复制为 `source/<source_sha256>.<ext>`。这个开关仅控制本地 staging，不代表已执行远程传输。

章节侧车不接受自由 CLI 路径。脚本按已验收文档的 `batch_id + source_item_id + document_id` 从 processing queue 与 `PAPER_INDEX.csv` 交叉读取并复核 queue 的 `sections_path/sections_sha256/sections_count`、索引的 `section_chunks_path/section_chunks_sha256/section_chunks_count/section_chunks_schema_version`，再写入 staging manifest；缺失或冲突都会失败。

目标已存在且 manifest/hash 完全相同时视为幂等成功；任一绑定不同则拒绝覆盖。

只同步派生文本时，源文件绑定标记为 `source_revalidation=deferred_to_mac`（兼容字段名，语义是延后到协调端）；从这种 staging manifest 建数据提取队列时，还必须显式加 `--allow-hash-only-source`。计算端只能产生 candidate，拉回协调端后，验收会强制重读原 PDF/XML 并核对 SHA-256；没有原文重验就不能 accept。若政策与任务明确允许全文跨机，也可使用 `--allow-copy-fulltext` 生成能在计算端立即重验的完整包。

## `sync_runtime.sh` 模式

所有模式默认都是 dry-run。只有检查输出且授权/许可/处理政策均明确后，才追加 `--apply`。

先在不入库的本地环境中设置目标：

```bash
export PAPER_SYNC_REMOTE_HOST='<ssh-target>'
export PAPER_SYNC_REMOTE_ROOT='<absolute-runtime-path-on-worker>'
```

### 工作流状态：协调端 → 计算端

```bash
scripts/sync_runtime.sh push-workflow
scripts/sync_runtime.sh push-workflow --apply
```

用于把 `ACTIVE_TASK.json` 和 `runtime/tasks/` 的只读协调副本提供给计算端。计算端不得将租约或队列状态反向覆盖权威副本。

实际发布先上传到远端临时区，再在远端协议锁内做内容寻址比较与原子替换；任务文件先
发布，`ACTIVE_TASK.json` 最后发布，避免计算端看到半套新状态。该模式排除提取队列、
人工复核表、验收与交付等可变协调状态；远端已有同路径文件若不符合已记录的 CAS
历史会拒绝覆盖。

### 处理输入：协调端 → 计算端

```bash
scripts/sync_runtime.sh push-processing-inputs <task_id>
scripts/sync_runtime.sh push-processing-inputs <task_id> --apply
```

只投影 `runtime/inputs/<task_id>/documents/`。目标必须显式配置为 `PAPER_SYNC_REMOTE_HOST` 和 `PAPER_SYNC_REMOTE_ROOT`；不得硬编码进公共文档。该模式的 `--apply` 还必须设置 `PAPER_PROCESSING_TRANSFER_POLICY=allow-remote-worker`。若投影中含 PDF/XML/CAJ 原文，还必须额外设置 `PAPER_FULLTEXT_TRANSFER_POLICY=allow-remote-worker`；解析文本授权不能替代全文授权。可用相应本地政策文件变量保存不入库的策略。任一目标或策略缺失时，脚本会在 SSH/rsync 写入前阻断；不得靠手工 `scp/rsync` 绕过。

### 计算结果：计算端 → 协调端

```bash
scripts/sync_runtime.sh pull-processing-results <task_id>
scripts/sync_runtime.sh pull-processing-results <task_id> --apply
```

拉取范围限于该任务的 `paperqa/` 和 `document_processing/` 结果，以及 `data_extraction/<job_id>/attempts/<attempt_id>/` 和 `data_extraction/<job_id>/receipts/<attempt_id>.json` 两类不可变提取产物；不拉取计算端的根 `result.json`、`validation.json`、人工复核、验收或交付投影。所有模式均排除 `*.sqlite*`、`*.db*`、`*-wal`、`*-shm` 和 `*-journal`；新处理模式还排除 part/partial/tmp/temp/download/crdownload/lock，并检查伪装扩展名的 SQLite magic，避免复制活跃数据库或未完成产物。

旧的宽范围模式已禁用：

```bash
scripts/sync_runtime.sh push-inputs
scripts/sync_runtime.sh pull-results
```

`push-inputs` / `pull-results` 会退出状态码 6；必须使用任务限定的 processing 模式，避免绕过传输政策和哈希边界。

每次成功的 `--apply` 都在协调端写入
`runtime/sync_receipts/v1/<mode>/<task-id-or-workspace>/` 的版本化同步回执，记录模式、
目标、文件数与快照哈希。同步回执只证明这次传输完成，不等于模型结果或研究结论已验收。

不论使用哪个拉取模式，“文件已拉回”不等于“结果已验收”。数据提取的固定顺序是：拉回结果 → 协调端合并完成回执 → validator → 生成人工复核队列 → 人工填写决定并回原文核验 → coordinator accept → 构建交付：

```bash
python3 scripts/merge_extraction_receipts.py \
  --root . --task-id <task_id> --actor-role coordinator
python3 scripts/validate_extraction_result.py \
  --root . --task-id <task_id> --job-id <job_id>
python3 scripts/make_extraction_review_queue.py \
  --root . --task-id <task_id>
# 人工填写 review_decision、source_verified、reviewer、reviewed_at
python3 scripts/accept_extraction_job.py \
  --root . --task-id <task_id> --job-id <job_id> \
  --actor-role coordinator
python3 scripts/build_extraction_delivery.py \
  --root . --task-id <task_id>
```

章节侧车用于路由，不是证据；验收还必须核对原文、解析文本、侧车和提取规格 hash，并回到原 PDF/XML、表格或图片。

## 传输政策未知时

下列任一问题未解决，都不得上传 MinerU 或传输到计算端：

- 出版社或机构许可是否允许将全文交给外部服务；
- 用户是否对本次输入给予了明确的外部上传/跨机传输授权；
- 目标计算端是否位于该任务允许的处理边界；
- 输入包中是否含有受限原文、补充材料或个人数据。

可以在协调端继续本地 XML 转换、生成 manifest 和 dry-run 计划。PDF 作业应留在 `waiting_remote` 或 `blocked`，并记录缺少的授权/政策；这是传输阻塞，不是论文无全文，也不是数据不存在。

## 冲突与完整性

- 默认预览每个 rsync 动作；不得省略检查直接 `--apply`。
- 常规运行数据使用“目标已有则保留”思路，不静默覆盖同名产物。
- staging manifest 和所有验收文件只存工作区相对路径，不把任一主机的绝对路径当作跨机身份。
- 传输前后以 SHA-256 校验内容，不以文件名、大小或 mtime 代替。
- 如果目标上已有同名但不同 hash 的文件，停止并进入冲突处理，不选“更新的那份”自动覆盖。
- PDF/XML、Markdown、章节侧车、元数据和模型结果都是不可信数据；同步成功不能把其中的命令或提示词提升为 Agent 指令。
